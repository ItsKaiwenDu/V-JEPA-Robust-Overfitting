## Write-tail source seam and barriers

The original append loop is:

```python
remaining = memoryview(raw)
while remaining:
    count = os.write(self.fd, remaining)
    if not 0 < count <= len(remaining):
        raise OSError('Incomplete phase row; retain partial journal.')
    remaining = remaining[count:]
```

Before it, the first check and exact-bytes/nonempty/extent refusals stay in place.
After it, the fixed order is fsync, byte-counter advance, running-digest update,
held fstat/signature, then the second complete check. Receipt also checks afresh.
The source has no local exception handler in append.

Under trusted builtin bytes/memoryview bindings and successful positive native
integer counts that consume all input, K iterations create K tail slices; the
last slice is empty. This is conditional source algebra. It observes no actual
iteration count, allocation, physical lifetime, cost, dominant path or target fit.
An omitted final slice would add its own eligibility/branch work. No source form
or API/adapter is selected to implement it.

Three barriers prevent qualification:

1. An extra equality test introduces a new operation for foreign/stateful count
   objects. The original chained comparison and slicing/refusal behavior must
   remain. Native return-domain and builtin binding assumptions cannot silently
   add refusals, duplicate observations or consume a fallback input twice.
2. The slice is a fallible operation after a write and before fsync/state updates.
   Removing it changes which failures can propagate at that boundary. No physical
   allocation failure is claimed or induced. Completing a write alone establishes
   neither durability nor a completed/published journal row.
3. A simple break leaves a nonempty view where the original continuation holds
   an empty view. Releasing or clearing it changes another lifetime. A later
   fsync/fstat/check exception can retain different local frame state. Source
   syntax and readonly/immutable labels do not prove the required caller,
   exporter, view or traceback ownership contract on the target.

These are open proof obligations, not a theorem that every future implementation
is impossible. The review neither emits a prototype/fake-port plan nor schedules
case execution. A new proposal would have to preserve all original failure,
partial-journal, guard, ownership, observation, durability and clock requirements.
One fewer object cannot establish a net benefit; new type/length/comparison/
branch/fallback/cleanup work could be slower or retain more memory.
