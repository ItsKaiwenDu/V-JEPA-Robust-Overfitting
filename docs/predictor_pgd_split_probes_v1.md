## New-source provenance and reconstruction

The original boundary can attach only inside original objective zero at
`EOT8-before`, to the actual projected full-input leaf. A new owner records its
identity/version/logical signature, checks it on exit and preserves mandatory
observer cleanup on failure. The frozen observer class stays exact; its original
private alias, native output, arriving cotangent, actual root/thread/hook and
restoration checks remain. Its new record kind prevents old capture identities
from qualifying. The new typed byte store publishes boundary metadata and eight
contiguous tensor copies with the reviewed 4 MiB file and 1,152-row limits.

The unbound source loader first runs the new numerical saved-value and native
proof readers against this run. It binds the numerical header, original objective
zero and boundary digests, joins the complete native calls/scopes, full-input
identity and actual perturbed pixel hash, and checks those source headers again.
Historical clean, interrupted or previous component captures cannot satisfy that
new source chain. These saved-value checks add no model objective, CPU gradient
or FP64 reference build. The metadata join alone cannot authenticate a caller's
dict; the actual source-pinned readers must be bound before any target execution.

Frozen CPU and CUDA reconstruction bodies are reused exactly. They restore
recorded strides, storage offsets and alias groups, fill unknown padding with
zeros and check every logical hash after all alias copies. Each backing allocation
is at most 16 MiB. Source version observations remain separate from reconstructed
version counters; the new route guards those counters throughout execution.
Physical native allocation addresses/alignment are explicitly not claimed.
The wrapper refuses changed live attention flags before any input reconstruction.
Device reconstruction matches both original AST and compiled body on the local
interpreter; a literal false compiler-import context preserves frozen code without
executing those imports during these checks. Startup source is unchanged.

## One component computation and durable completion

Each fresh role executes one forward and one outer VJP through the frozen route.
The candidate adds its one existing owned inner math VJP. There is no warmup,
untimed control, replay, completed-cohort repeat or oracle/reference build.
The route retains actual outer/inner GraphTask, root/three-leaf, first-order,
exact-token, flags/modes/hooks/.grad/version/RNG and single-use requirements.

The component journal records startup, source checks, reconstruction, route and
profiler entry, forward/backward, CUDA synchronization, profiler shutdown, route
closure, ownership/return publication, raw extraction/publication, semantic
validation, restoration and terminal publication. It is an exclusive 0600 fsynced
64 KiB / 64-row / 1,024-byte-row chain in a private directory. Mandatory cleanup
continues after journal errors. Every phase uses the same continuing deadline;
profiling, extraction and publication do not receive a new clock.

The raw 4 MiB / 20,000-record envelope is saved before semantic validation. The
existing hybrid reader checks source thread/sequence/producer ancestry and exact
GPU-host launch links. Unsupported metadata remains saved and rejected. The
component record binds four bounded return files, route proof, raw trace,
manifest, backend assessment, startup and resource receipt. Completion readback
requires expected byte digests, exact paths, all durable returned stages, no
failure marker and a backend assessment reproduced from the immutable raw bytes.
A marker alone cannot qualify completion. These are component metadata records;
geometry accuracy, actual CUDA execution, full EOT8 backend coverage, replay,
performance, cost, adoption and training admission stay false.

## Parent resource core

The parent monitor accepts an already-launched, still-owned child; it spawns no
process. Its fixed launch-origin phase deadline covers all worker startup and
finalization, with at most 120 seconds. It samples observed process-tree RSS and
stops the launch above 4 GiB, after a failed storage/GPU gate, or on deadline/error.
The existing 7 GiB CUDA allocator cap remains owned by the unchanged startup.
Up to two seconds of termination grace uses existing overall overhead and never
extends the original overall work deadline.

Owned root/descendant handles check user, birth, parent and session metadata before
and after binding. Termination uses only the held process descriptors; there is
no numeric-PID signaling fallback. Handles close after success or failure.
The RSS reader sums `smaps_rollup` resident memory across observed processes,
including children of observed threads and descendants. Shared pages are counted
conservatively more than once across processes. Normal running/sleeping state
changes do not replace a process's birth identity. A disappeared child can no
longer contribute a current sample. Unexpected parent/birth/UID changes refuse.

These choices follow the [Linux proc documentation](https://www.kernel.org/doc/html/v6.11/filesystems/proc.html)
and Python's [PID descriptor](https://docs.python.org/3.11/library/os.html#os.pidfd_open)
and [descriptor signal](https://docs.python.org/3.11/library/signal.html#signal.pidfd_send_signal)
APIs. The kernel documents child-list races, so enumeration is not exhaustive.
RSS polling can miss transient peaks and is not an instantaneous address-space
or kernel quota. Target kernel/API availability and actual stop behavior have
not been observed here; unsupported target APIs must refuse before a new launch.
