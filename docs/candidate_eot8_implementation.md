# Opt-in EOT8 evaluation and benchmark preparation

The separate `candidate_*` modules implement the proposed PGD20/R2/EOT8/score4
path for bounded diagnostics. The historical evaluator, calibration code,
study YAML, diagnostic panel and failure evidence remain unchanged. The frozen
[candidate proposal](research_attack_candidate.md) still has no selected
research step size and grants no research or spending authorization.

The new evaluation settings include an explicit profile. PGD20 and the PGD50
stronger control share the same eight attack draws and both restart starts.
Scoring uses four independent draws; optional audits stay separate. The attack
bank alone selects perturbations. All 200 calibration mask seeds match the
proposal in the actual upstream seed space. Each checkpoint gets fresh attacks.

The per-clip journal is atomic and resumes only an identical contract. New
calibration, schedule, anchor and feature consumers bind the candidate profile,
61 source/metadata inputs, data identity, model weights, target, selected
diagnostic step and execution runtime. CUDA provenance additionally binds the
GPU model, physical UUID and driver. Old four-draw calibration, legacy caches
and anchors, changed source/runtime and stale receipts are refused. Initialization
and earliest exact ties remain part of complete primary-validation selection.

The bounded three-step bundle chooses among 0.5, 1 and 2 per255 using independent
main mean, then smaller step on an exact tie. It is a **one-clip diagnostic**.
Full research calibration execution and research trajectories are deliberately
gated. The required 30 evaluations on the original first ten training-monitor
rows must wait for chosen-runtime and economic qualification. Neither a CPU
fixture nor a one-clip diagnostic supplies the research step size.

The prepared hardware packet is under
`runs/pretrained/diagnostic/candidate-eot8-handoff-v3-20261028/`. It includes the
source snapshot, verified original 100-training-clip archive, Linux dependency
wheels, pinned upstream Git bundle and unchanged restoration code. It contains
no SSH keys or confirmation/test pixel files. The released checkpoint is a
checksum-pinned setup input, not embedded in this packet. PyTorch/CUDA must
remain the qualified 2.8.0 template stack; the provided wheels do not replace it.

Its required phases are the unchanged numerical preflight, a one-clip three-step
bundle, three pretrained primary units plus a routine unit, clean and adversarial
two-update recovery with fresh resume/reference processes, primary units on
both trained anchors, matched primary/PGD50/FGSM/random controls, and initial and
trained feature/probe units. Save/load spans, exact logical-state signatures and
allocator peaks are retained. These are bounded representative units, not a
complete study cost bound or a full training qualification.

The runner requires a new checksum-pinned launch file and reconciled ledger.
It checks one sufficient-memory GPU, at least 40 GiB usable system RAM, 55 GiB
free after inputs, a 30 GB container and 80 GB volume at `/workspace`. Deployment,
setup and idle time count toward the proposed two-hour limit and chosen dollar
allowance. The $10 pilot envelope is counted once within the unchanged $160
compute/$200 total caps. Earlier case windows and recovery grants are not reused.
The parent stays CPU-only, workers run in separate process groups, and each
worker has its own fatal deadline even if SSH or the parent disappears. Neither
the timer nor the parent stops Runpod billing; evidence must be copied and the
Pod terminated manually. There is no automatic retry or fallback after failure.

found its missing staged-proposal dependency chain. It remains unapproved.
The corrected package verifies that chain; the final version also includes the
independent worker timer. Earlier packages and checks are retained as history.
